# 06 · API Reference (v0)

Current Explore policy: [Explore simplification](15-EXPLORE-SIMPLIFICATION.md) supersedes older active-only/eligible/source-fresh admission, separate watchlist, cost-hint quotas and six-card visibility rules below. Only a confirmed past deadline hides a result. Other details remain warnings/ranking factors. SQL stores search links before enrichment; unreadable details produce visible unconfirmed results. Source evidence, privacy, proposals, knowledge scope and AI limits remain enforced. This simplification adds no schema migration.

Base URL `http://localhost:8787`. JSON in/out. Auth: HttpOnly account-session cookie; `x-student-id` is a migration fallback for unlinked legacy browser profiles only. Errors: `{ error, details? }` with 401/403/404/409/415/422/429/502/503.

## Replit pilot access and AI caps

All `/api/*` routes except config, access validation, health, session inspection, phrase sign-in, recovery and logout require either a valid account session with a still-allowed setup code, or `x-access-code` when `ACCESS_CODES` is configured (always required in production). Codes are comma-separated, trimmed, case-sensitive secrets; invalid or revoked codes return 401. Account sessions identify the student across devices; unlinked legacy profiles still require `x-student-id` and their original code until linked. A tester code alone never signs into a phrase-linked profile.

- `GET /api/config` (public): `{accessRequired, feedbackUrl}`; never exposes allowed codes.
- `POST /api/access` (public): `{code}` → `{ok:true}` or 401. The client stores the accepted code in sessionStorage and sends it with subsequent requests, including downloads.
- Student setup records `Student.accessCode`. It is excluded from profile responses and included only in the student's full data export.
- Buddy messages, extract, coach, and Today insight reserve one AI request before invoking a configured provider. Consent and AI-disabled behavior remain unchanged. `AI_DAILY_LIMIT` defaults to 20 per student per UTC day; `AI_MONTHLY_LIMIT` defaults to 1000 shared requests per UTC month. Both accept non-negative integers, including zero.
- A reached cap returns 429 with friendly `{error}` copy. Failed provider calls count; internal tool rounds/retries do not add feature requests. Transactional persistent counters prevent concurrent overspending. Other routes remain available. Deleting a profile removes its daily counters; anonymous monthly totals remain.

Production serves the built website and API from one origin/port; see `DEPLOY-REPLIT.md`.

## My applications
`GET /api/applications` lists the student's saved tracker with deadline provenance/countdown/checklist progress. `PATCH /api/applications/:opportunityId` accepts status (interested/preparing/applied/result), deadline (real YYYY-MM-DD or null), private notes and checklist [{title,done}]. `POST /api/applications/:id/prep` proposes reminders/study blocks only in real free time before the known deadline; no fallback booking or AI is used. Approval revalidates with the existing engine. Today returns `dueSoon` for active applications within seven student-local days. Saving an opportunity pre-fills checks plus official-deadline confirmation.

## Calendars and week view
`GET/POST /api/calendars` lists masked links or adds `{label,url,eventType?:class|personal|other}` and performs an initial sync. `POST /api/calendars/:id/sync` refreshes the mirror; `DELETE /api/calendars/:id` removes it and its imported events without changing the provider. URLs accept HTTPS/webcal, never credentials or private-network destinations; redirects are rechecked, DNS is pinned, and responses are limited to 2 MiB. Public URL validation does not promise provider availability. `GET /api/week?from=YYYY-MM-DD` returns seven student-local days, load, clashes and events. Imported events reject direct edits/deletion and agent move/remove proposals. They feed the same engine as manual events.

`GET /api/week?weekOffset=0` returns the student's current Monday–Sunday week; integer offsets -5200 through 5200 navigate whole weeks relative to that Monday. Date arithmetic uses the student's timezone, independent of browser/server date. `from` remains a rolling seven-day start; omitting both parameters still starts at student-local today. Supplying both or an invalid date/offset returns 422. Response remains an array of seven `{date,minutes,load,clash,events}` objects with `Cache-Control: no-store`; each event now includes `id,title,type,start,end,source,readOnly,done,recurring,clash`, matching Today timeline details. Authentication and student filtering are unchanged; GET consumes no AI usage and writes nothing. The UI uses the existing `PATCH /api/events/:id {done:boolean}` for supported writable non-recurring items and the existing explicit Add event form for the selected date. No new schema or environment setting is required.
Calendars expand from 30 days back through 180 days ahead, at most 3,000 occurrences, honoring TZID/RRULE/EXDATE/RECURRENCE-ID. Floating times use X-WR-TIMEZONE or student timezone. High-frequency rules fail visibly instead of exhausting the server; prior data remains intact. All-day items become date markers, not 24-hour class blocks. A persistent lease coordinates 3-hour syncs; a minute poll starts on boot.

## Timeline deletion and sparks

The Timeline minus button uses the existing `DELETE /api/events/:id`: 204 on success, 404 for absent/another student's event, 409 for read-only calendar imports. The client confirms a named event or explicitly the whole recurring series, then reloads Today/Week. This deletes the stored recurring event, not one occurrence. No external calendar is changed.

`GET /api/words?offset=N` requires a student and a nonnegative integer offset through 100000 (default zero); invalid input returns 422. Response `{date,word:{word,pos,meaning,example},position,total}` starts from that local day's word, advances through 500 curated words and wraps after the full set. Today uses the same daily selection. Cache-Control is no-store; practice has no saved progress, AI reservation or audit write.

`GET /api/news` requires a student, is uncached and never fetches feeds. Production returns real `isSample:false` rows; demo mode can include seeded examples. Explicit `POST /api/news/refresh` checks the student's topic feeds without transmitting profile fields to publishers, then returns the same snapshot plus `refresh:{status,succeeded,failed,skipped,saved,feeds:[{feed,state,saved,reason}]}`. Status is refreshed/partial/cached/unavailable; state is refreshed/cached/failed and reason is null or timeout/source_unavailable/unreadable_or_empty_feed/storage. Saved counts are processed upserts, not necessarily new articles. Atomic shared feed cache is 15 minutes; failures back off one minute. A concurrent request can return cached while another fetch is in progress. At most seven fixed feeds, 30 entries each, recent 30-day dated articles only. Feed failures preserve real stored stories and return a friendly outcome; request/database errors still use normal HTTP errors. Refresh is audited and uses no AI allowance or API key. UpdatedAt is the stored check time, not a promise of new publication. Word/news controls work with AI disabled.

## Installation and gentle notifications
`GET /api/notifications` returns preferences, student timezone, subscription count and public VAPID configuration (never private key/subscription URLs). `PATCH` accepts enabled, time (07:00–20:59), pauseWeek boolean. `POST /api/push/subscribe` saves a browser-generated HTTPS push subscription (vendor endpoint allowlist, encrypted at rest with the VAPID private key); `POST /api/push/unsubscribe` removes that student's endpoint and disables nudges if no devices remain. `POST /api/notifications/test` is an explicit action, respects opt-out/pause/quiet hours/classes, and consumes the same local-day allowance. Responses distinguish accepted by service, not delivered, unconfigured, quiet/paused and already sent. Never claim device delivery from an HTTP acknowledgement.
The minute scheduler evaluates each student's local chosen time, retries evaluation after class ends but not after 9pm, and reserves a unique student/local-date delivery before external sends. Failures/crashes are not retried automatically: at-most-once takes priority. Selection is deterministic: active application due within three days → exam/deadline tomorrow → pending approval → light-day goal suggestion → nothing. A service worker also suppresses delayed notifications on another date, in quiet hours or during the class snapshot carried by the nudge. Settings are off by default and require a student browser permission gesture.
The service worker caches only public HTML/JS/CSS/icons, never APIs or student data. Offline opening shows a shell and connection guidance; data/features still require the server. Notification clicks choose only an allowlisted app tab.

## Private phrase sign-in and recovery

| Method | Path | Contract |
| --- | --- | --- |
| GET | `/api/auth/session` | Public, no-store; `{student: Student or null}` from the account cookie. |
| POST | `/api/auth/login` | Public: `{phrase}` → existing Student and HttpOnly session cookie. No invitation, username, or student ID needed. |
| POST | `/api/auth/link` | Current unlinked legacy browser profile plus original invitation: `{phrase, confirmPhrase}` → same Student plus one-time `recoveryCode`. |
| POST | `/api/auth/change-phrase` | Signed-in session: `{phrase, confirmPhrase}` → same Student plus a new one-time recovery code. Revokes every old session and recovery code, then signs this device back in. |
| POST | `/api/auth/recover` | Public: `{recoveryCode, credentials: {phrase, confirmPhrase}}` → same Student plus replacement recovery code and a session. Recovery codes are single use; old sessions/phrase are revoked atomically. |
| POST | `/api/auth/logout` | Revoke this device's session and clear the cookie; 204. |

`POST /api/students` accepts `credentials: {phrase, confirmPhrase}` (required in production; optional for legacy local/demo compatibility). Phrases are 12–128 characters after Unicode normalization, trimming, collapsing whitespace and lowercasing; input is capped at 128 characters. Confirmation must match. The secret phrase must be unique across profiles; conflicts return 409. Failed sign-in/recovery returns generic 401. Removed tester invitation codes still revoke sign-in/session access.

Only keyed HMAC-SHA256 hashes of phrases and recovery codes are stored, using a persistent server-only `SIGN_IN_SECRET` (at least 32 random characters in production). This key must stay stable across deployments/instances and be backed up separately from the database; changing it makes existing phrases and recovery codes unusable. Development has a clearly local-only fallback. No raw phrase/code appears in ordinary profile responses, exports or logs. Profile responses expose only `hasSignIn`; a recovery code is returned only when created or replaced. The random 24-byte recovery code is displayed once with a Copy button and save acknowledgement.

Throttling for login, recovery, registration and phrase changes persists across instances: 100 attempts per IP per 15-minute window, 10 per credential hash per 15-minute window, and 500 shared per minute. Exceeded limits return 429; changing guessed phrases cannot bypass the IP/shared limits. Production trusts only the nearest reverse-proxy hop for the client IP. Mutation Origin checks protect cookie-authenticated requests.

Sessions last 30 days with `HttpOnly; SameSite=Lax; Path=/` and `Secure` in production. Only a SHA-256 hash of each random 32-byte session token is stored. Expired sessions/counters are pruned, profile deletion cascades sessions, and account state changes are audited. Invitation codes are required only to create/link profiles and for legacy browser-ID migration. Returning signed-in students open Today; others see phrase sign-in before any invitation gate. Temporary load failures preserve the remembered profile and offer retry. Students who lose both their phrase and recovery code can change their phrase from a signed-in device; without one, there is no identity-based recovery because no email is collected.

### Sign-in integration with notifications
The browser sends its optional push endpoint with `/api/auth/logout` so the server can revoke this student's device subscription before ending the session. Changing/recovering a private phrase revokes all subscriptions and turns nudges off alongside invalidating old sessions. Students can opt in again on their trusted devices. Onboarding includes both an optional calendar step and required phrase confirmation; the recovery code is still shown once before the dashboard.

## Active-only Explore and student-scoped knowledge

- `GET /api/config` adds demoMode (default false). Onboarding ignores sampleWeek unless true.
- `GET /api/today` adds student-local greetingPart and dueSoonEvents (exam/deadline events within seven days); nextAction is null with no suggestion. dueSoon remains Interested applications. The client renders glance → next step → spark.
- Today returns `Cache-Control: no-store`. Metric keys stay `focus`, `freeTime`, `progress` for compatibility. `focus.label` is **Study planned**: `minutes` is today's scheduled Study-event duration (including done blocks), `limit` the daily study limit, `pct=minutes/limit` (zero for a zero limit; may exceed one when over limit). This is planned time, not measured completion.
- `freeTime.label` is **Free time left**. `minutes=inWindow` is future unbooked study-window time only, excluding protected rest. `windowRemaining` is the remaining study-window duration before subtracting bookings/rest; `pct=minutes/windowRemaining` (zero when no window remains). `downtime` is future unbooked protected-rest minutes, `downtimeRemaining` the full future rest window, and `downtimeBusy=downtimeRemaining-downtime` the union of calendar overlaps. Downtime is shown separately and never added to `minutes`. Values are nonnegative whole minutes in the student's local calendar day. Past portions and zero-duration deadline markers do not consume remaining time; overlapping bookings count once. Overnight windows contribute only their portions inside today.
- `progress` is unchanged: done/planned goal milestones for the current Monday–Sunday week (target date in the week or completed in the week). `capacity` retains full-day planning semantics. The visible Today page re-reads the snapshot every minute and on return/focus, without calling `/api/today/insight` or reserving AI usage. Insight also uses student-local dates.
- `GET /api/opportunities` returns active eligible picks, fit/countdown/cost/Verified fields, interestedCount, canAskAll, knowledgeStates (program ID → ready/preparing/unavailable), preparing and independent knowledgeUnavailable. Before any search or prior picks it returns an empty picks array and an explicit search action. This GET never enqueues a search. It includes catalog `{complete,free,paid,missingInterests}`: active, source-fresh, eligible good matches excluding saved/dismissed items. Complete coverage requires each selected interest plus the combined Free/Paid targets. No paid models run during this GET. Discovery fields include discoveryEnabled, unavailable, finding, limited, error, resultIds, lastCheckedAt, refresh and search `{phase,found,detail,startedAt,finishedAt}`. Failed searches return safe errors rather than claiming refreshed results.
- `POST /api/opportunities/refresh` returns **202** with requested/requestId plus status. Both first Search and Search for more check the catalog first. A full catalog returns usedSharedCatalog=true, requested=false and selected resultIds with no web work or allowance debit, even with AI consent off, missing setup or reached caps. Otherwise only missing interests/buckets are queued. Coverage checks every selected interest; at most five topic groups are queued per request, and any remaining gaps still require the usual allowances. The first successful search is initial; subsequent web searches reserve a manual base/bonus slot, and successful complete/empty settlement charges once. Failed/limited/cancelled searches leave the allowance intact. For needed web work: consent off → 403, no interests → 422, manual allowance/global cap → 429, missing search setup → 503. A capped initial request returns 202 with limited status. Catalog refills use no AI. The worker rechecks coverage before funding a queued group and can settle it cached without charging a manual slot. Calls for the same pending request coalesce.
- `POST /api/discovery/run`, authenticated, strict empty JSON `{}`: bounded request work for the student’s own persisted search groups and program preparation. No client-selected groups/program list. Returns skipped if locked, otherwise discovered/prepared counts. Provider attempts run only under the shared lease and budget reservations. Explore sends sequential bounded work calls and polls stored status every 2.5 seconds; a configured timer/cron may continue work.
- `GET /api/discovery/status` returns enabled/unavailable for AI consent + search configuration, independently of embedding/index readiness. It settles finished requests and reports the real current request, not merely a historic group error. Search phases: idle, queued, searching, reading_sources, checking_facts, indexing, cached, complete, empty, failed, limited, cancelled. Status reads call no paid AI models.
- `POST /api/opportunities/:id/status` accepts saved/dismissed/none with an optional controlled dismissal reason. Interested pins source-backed requirements/citations/deadline on creation, preserving existing notes/completed work. Removing a card deletes the derived pick immediately; the next list read refills its bucket with no AI. Interested applications remain even after expiration.
- `POST /api/buddy/messages` accepts `{text,conversationId?,opportunityId?}` or `{text,conversationId?,scope:"my_opportunities"}`. Scope/opportunityId are mutually exclusive; arbitrary ID-list fields are rejected. SQL recomputes membership from current active StudentPick + non-dismissed Interested records and explicit feedback; outside-set requests/follow-ups return 403 before an AI charge. Conversations inherit their saved scope. Cross-program replies are grouped by name and include scope and programs `{id,name,canAddRequirements}`; single-program replies include opportunityId. Citations include number, optional chunkId, opportunityId, sourceUrl, pageTitle, checkedAt. Structured facts are SQL/rules output, textual claims are verified excerpts, with at most three retrieval/model rounds. Existing daily/monthly AI request caps apply.
- `POST /api/opportunities/:id/requirements` requires membership, creates an AWAITING_APPROVAL source-backed proposal, and execution also requires an Interested application with unchanged evidence. Unknown/currently stale evidence → 422. Approval merges checklist steps and citedDeadline while preserving user notes, dates and completed steps. No external application is submitted.
- `POST /internal/jobs/run` accepts the owner bearer JOBS_SECRET (at least 32 characters), no student session. Missing setup → 503, wrong bearer → 401. Returns skipped if leased, otherwise `{expired,refreshed,discovered,prepared}`. Timers and cron share the same lock. Monthly refresh never alters Interested records; source checks run monthly and at the seven-day deadline boundary.

Search and preparation attempts reserve the overall AI_MONTHLY_LIMIT without charging a student’s daily counter. DISCOVERY_MONTHLY_BUDGET additionally limits search runs. DISCOVERY_RECHECKS_PER_MONTH bounds both source rechecks and standalone program preparation. Global reservations include failures; manual successful-search allowances are separate. AI_DISABLED disables all paid work. Budgets are attempt counts, not dollar ceilings. Setting DISCOVERY_ENABLED=false stops web search while deterministic catalog reuse and existing configured program Q&A/preparation can still work; use AI_DISABLED=true or zero overall allowance to stop all paid calls.

Knowledge readiness checks the index dimension/metric without calling a paid model. Optional failures show fixed setting-name explanations and retry connection checks after one minute. SQL snapshot/model/store checks prevent obsolete vectors from becoming answers. General workflow records contain controlled stage/reason metadata only. Public vector/chunk data has no student fields; private request state is included in export and cascades on deletion.

Foreground work handles a search group or a standalone program preparation per call, keeping slow providers within the web request window. Timer/cron work shares a three-minute run deadline, checked before funding another stage; a final in-flight provider call can finish after that deadline. Paid nodes are never automatically replayed.

## Shared search allowance recovery

Discovery status and opportunity lists now include `monthlyAllowance: {limited, reasons, resetsAt}`. Reasons are `discovery_monthly_limit`, `ai_monthly_limit`, or both. Status checks read the current UTC-month usage and current deployment limits without making a provider call, changing counters, or using a student’s manual allowance. `resetsAt` is the next UTC calendar-month boundary; `refresh.nextAvailableAt` remains the separate rolling student cycle.

Raising either cap only clears a blocker if all reached shared caps now have room. A saved historical limited request no longer disables the control indefinitely. Clicking Search can queue previously unfunded work again, retaining its prior manual intent and charging the student’s manual allowance only after success. If the shared catalog has filled, reuse it without a paid search. A spent personal allowance prevents further web work but does not prevent full catalog reuse. Funded provider failures remain failed and require an explicit retry; they are not replayed by this recovery. Timers do not start orphaned limited_manual groups without a new live request.

The screen identifies shared limits and displays the calendar reset in the browser’s timezone while preserving existing picks. A rejected manual refresh reloads allowance state. No database migration, new Secret, automatic limit increase or counter deletion is introduced.

## Extraction reliability and owner diagnostics

OpenAI opportunity extraction uses a strict JSON schema rather than JSON mode alone. Required fields, types, enums, bounds and nullable evidence are provided to the model; the response still passes Zod and the deterministic official-evidence verifier. Null evidence is omitted from the local evidence map and never verifies an unsupported fact. Other providers retain local schema/evidence validation. Extraction has a 4096-token text allowance (nano additionally retains its existing 4096-token reasoning headroom), compact evidence quotes and no automatic hosted retries or fallback to loose JSON.

An OpenAI deployment without either AI_MODEL_EXTRACTION or OPENAI_MODEL reports `extraction_not_configured` before a paid search. An omitted extraction override still inherits Buddy's configured model. Run usage JSON records the requested search/extraction provider and model IDs in `models`, never keys. Failures distinguish missing_model, invalid_json, invalid_schema, incomplete_response, refused_response and extraction_error; SDK connection failures and timeouts are identified by their constructor type even when Error.name is generic. Schema diagnostics contain at most eight allowlisted field paths and issue codes; incomplete responses record a controlled finish reason. Unexpected exceptions record only a controlled error class and, when available, an allowlisted application file/line. Raw errors, output, rejected values and prompts are not stored. Historical runs cannot acquire their original model IDs retroactively.

Zero saved programs plus an operational extraction/provider failure now marks both the run and request failed instead of presenting the run as complete/empty. A genuinely empty search or evidence-only rejection remains an honest empty result. Failed paid attempts stay counted globally and do not consume a student's successful manual-search allowance. No paid work is automatically replayed.

The owner can run `npm run check:extraction` in Replit Shell for a no-call configuration check, then `npm run check:extraction -- --live` for a single hosted extraction request against synthetic text followed by local evidence verification. This CLI is separate from student endpoints and app quota counters, can incur a small provider charge only with --live, and never queries or writes the database, fetches official pages, stores the fixture, or indexes vectors. It tests the current Shell environment, which may differ from production.

## Source reading and search diagnostics

`GET /api/discovery/status`, opportunity lists and refresh responses include `diagnostics` for the signed-in student's current request bindings. It reports distinct runs, provider search attempts, HTTP attempts (including robots/redirects/supporting pages), recorded candidate counts, completed/failed search/fetch/extract/verify/save/index steps, unique recorded saved IDs, grouped controlled failures and requested model snapshots. Missing historical candidate counts are null; missing historical model IDs are not inferred. Reading this summary makes no provider call and does not replay work or rewrite old usage.

The summary includes all relevant failures rather than just the first candidate's error. The primary message prioritizes actionable setup/provider errors and later processing failures over an early unsupported document. Existing failed requests can therefore show a more useful error derived from their original run history. Summaries contain only controlled codes, media/encoding categories, allowed field paths/classes and sanitized model IDs: no raw errors, page URLs, source hosts, output, headers or credentials. Unrelated students' requests/runs are excluded.

New verification failures include `verification: [{field, reason}]`, identifying required facts that blocked acceptance. Reasons distinguish missing facts, a source URL not among fetched pages, a quote not present on the page, unsupported values, an unreviewed organizer domain, invalid grades, missing current activity and an expired deadline. Older failures cannot acquire these details retroactively. The public summary allowlists both properties and excludes raw values; the internal run can retain the already-public source hostname for owner review. Verification failures outrank incidental source errors and processing exhaustion in the primary message, while configuration/provider/extraction/storage errors remain actionable priorities.

Scout numeric grade ranges accept literal continuous ranges/lists, and an explicit high-school audience can establish school eligibility without inferred bounds. Organizer and format may remain unknown; strict online-only preferences require confirmed online participation. Active partial candidates appear with Needs checking/sourceReadAt and null sourceCheckedAt. Announced future openings are separate watchlist entries. Dates, costs, status and source confidence remain deterministic.

`PATCH /api/me` accepts optional partial `discoveryPreferences`: city/state, radiusMiles (default50), format (both/online/in_person), goals, personalProject, hoursPerWeek, maxCost, currency USD. Unknown hours/max cost are null, never zero by default. City excludes street-address characters, state uses the US allowlist. Profile format and preference format are synchronized. Saving reranks existing catalog picks without new provider calls and cancels outdated queued search intent; it does not grant an extra search for every preference edit. Export includes the student's preferences and score records; shared research never includes their private text.

`GET /api/opportunities` additionally returns `watchlist` (up to six announced future openings, outside active picks), each card's `sourceReadAt`, `sources[{field,url,quote}]`, parsed qualificationNotes and publicFacts. `verified` requires verified status and sourceCheckedAt. Paid includes tuition-free-with-required-extras and unknown prices with explicit labels. Up to 3 Free and 3 Paid total; feedback/refills require no paid work. New Scout runs record per-field rejection reasons, persisted stages, actual token metadata where available and full public candidate audit.

Owner-only `GET /internal/diagnostics` uses JOBS_SECRET Bearer authentication. Optional `runId` includes that run's public pages/assertions; default latest-five summary includes public names/URLs/outcomes, query/context, configuration presence, current caps/usage, model identities, durations/tokens and estimated cost. No provider calls, vector connections or writes. No Secret values or student identity/private text. Query-string secrets are rejected.

Owner-only `POST /internal/diagnostics/test-scout` has strict `{mode:"configuration"|"fixture"|"live"|"advance",runId?}`. Configuration/default and fixture return200 without provider calls/catalog writes. Live reserves normal shared usage, queues at most one public coding candidate and returns202/runId; no live call is started until bounded advance/authorized worker. One research plus one extraction request maximum; no format repair in this small test. Repeated live requests reuse an active diagnostic job. Advance requires that diagnostic runId and processes one network stage under the shared lease. Missing/invalid owner Secret →503/401; missing setup →503; cap →429; arbitrary run →404. No student-supplied context or ID allowlist is accepted. See [Scout](14-OPPORTUNITY-SCOUT.md).

Research-error diagnostics additionally expose optional `operation`, controlled `providerCode` and an allowlisted `providerParam`. Schema issues use specific safe paths such as `candidates.item.officialUrl`; raw provider messages/rejected values are excluded. Older rows remain unchanged. Research lead envelopes/optional metadata are normalized locally without inventing facts; valid siblings survive an invalid URL. OpenAI format repair uses an HTTPS pattern rather than unsupported `format: uri`, with full URL validation still on the server. Caps/retries/qualification and database contracts are unchanged.

## Explore partial-results API update

Source admission additionally rejects known Maps/search listings; actual program links with uncertain facts still qualify. Existing listing records remain stored but do not count toward picks or shared coverage. A current-cycle personal successful-search charge for listing-only results restores once; global paid usage is retained. See [recovery](21-EXPLORE-RECOVERY.md).

## Knowledge preparation recovery

Pinecone status adds `indexDetails:{api:"vectors"|"documents",input:"vectors"|"text",field}` (null for adapters without these details). Opportunity lists add `knowledgeDetails: { [programId]: {state,reason,message,retryable,resetsAt?} }` alongside compatibility `knowledgeStates`. Reasons distinguish setup/storage/source unavailability, active work, failed/unknown work requiring owner retry and current shared preparation/AI caps. Ready means matching SQL source/model/store chunks; it does not independently probe Pinecone on each student list. Supported facts older than 30 days display as stale. Saved-text ingestion preserves original check dates.

`GET /internal/knowledge/status?opportunityId=...` requires owner `JOBS_SECRET` authentication and strict optional public program ID.
